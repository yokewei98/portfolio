WA Agent

A self-hosted, business-agnostic WhatsApp AI sales and support assistant. It answers enquiries in the customer's own language strictly from an operator-controlled catalogue, and steers each conversation toward a captured lead.

The problem

Enquiries from paid ads land on WhatsApp, where they go unanswered overnight, get answered slowly, or get answered differently depending on who picks up the phone. Whatever is agreed stays inside a chat thread — so the name, the item, the date and the time never reach anything anyone can report on.

The business pays to generate the lead and then loses it in an inbox. The fix has to work without a WhatsApp Business API contract, without a server to maintain, and without a developer standing by every time a price changes.

Key decisions

  • The business is data, not code

    The engine ships neutral and knows nothing about any particular trade. Persona, catalogue, fact base and the definition of a lead — including which fields must be filled before something counts as one — all live in a Google Sheet. A business type is a preset that seeds those tabs: property, venue, services, or a blank custom start. Adding an industry the system has never seen is one more preset composed from six documented building blocks, not an engine change. The practical effect is that the operator owns the content, not a developer: a price edit in the catalogue tab is live in about sixty seconds, with no build and no deployment.

  • A transport layer that knows nothing

    The relay that talks to WhatsApp runs on the operator's own PC; all the reasoning runs in Apps Script. The line is drawn so the relay holds no Gemini key, no database credentials and no business logic — it pairs the phone, batches messages and forwards them. The machine most likely to be left unattended in a back office is therefore the one with nothing worth taking, and the brain can be rewritten, or a second client added, without the transport changing at all.

  • Burst debouncing as both cost and quality control

    People type on WhatsApp the way they talk — four short messages, not one paragraph. A ten-second per-contact debounce collapses that burst into a single webhook and therefore a single model call. It went in to hold token spend down, but the larger gain was quality: the agent answers the whole thought instead of replying to the first fragment and then contradicting itself twice.

  • Refusing to invent answers

    A blank cell in the Sheet means unknown, and unknown means the agent stays silent on that point rather than guessing. It logs a KnowledgeGaps row and alerts the control group, so a person answers that customer and the missing fact gets written down once. Handing a confidently wrong price to a buyer is worse than a short silence — and the by-product is a standing queue of what customers keep asking that the business has never documented.

Deeper technical detail

One engine, three modes. A single setting in the Sheet selects the behaviour: lead_capture answers from the catalogue and extracts booking fields; answer_handoff answers from a knowledge base and escalates to the right person by category, relaying their reply back and closing the ticket; and content_prep is a group assistant that picks photos and drafts captions. Three products' worth of behaviour without three codebases.

Multi-tenant by design. One Node process hosts every client's WhatsApp session behind one multiplexed send router and one shared Cloudflare tunnel, with isolated per-project auth stores and secrets so sessions cannot cross-wire. Three sessions run live. The alternative — one relay and one tunnel per client — multiplies the running cost by the client count for no benefit.

Resilience in the transport. A SQLite-backed retry queue with exponential backoff persists both inbound webhooks and outbound sends when Google or WhatsApp is unreachable. Message IDs are deduplicated, and the relay suppresses its own echoes with a five-minute self-sent TTL. Failed sends retry every minute; queue dispatch and a relay health check run every five; a daily 09:00 Drive backup keeps thirty days; and ten minutes of silence from the relay triggers a Telegram alert out-of-band, so the channel that reports the outage is not the one that is down.

Compliance built into broadcast. Bulk sends exclude opted-out contacts, enforce a three-day per-contact cooldown, stagger at thirty-second spacing inside a 10:00–20:00 window, and require an explicit preview confirmation before anything leaves. A single opt-out keyword adds the contact to the ignore list and drops their already-queued sends.

Fitting the client, not the reverse. The engine reads and writes by live header rather than fixed column index, so it adopts a client's existing tab names and column layout with no data migration. Human takeover needs no command either: when the operator replies manually from their own phone, the relay flags it and the next turn's history carries it, so the agent stays consistent with the person instead of talking over them. Trilingual throughout — Chinese, English and Malay — and multimodal, reading voice notes and images directly. Backed by 706 test cases across 73 files, roughly 12,100 lines of test code.

The arc — spreadsheets, then an ERP

The agency already ran on spreadsheets. Rather than propose a rewrite nobody had budget for, I automated the sheets in place — contract generation, permission setup, metric collection and payment consolidation became scripted actions on the documents the team was already using. Nothing had to be migrated and nobody had to be retrained, which is the only reason it was allowed to happen at all.

It ran that way for over a year, and the limits it eventually hit were the platform's, not the workload's. Every new campaign meant another tab — the roster reached 105. Cross-workbook joins were IMPORTRANGE formulas with no referential integrity behind them. And the only way to express the client may not see this was to omit a column or lock a range: effective, but not auditable, and it does not compose.

The Creator ERP is the same domain rebuilt once those became the binding constraint — campaigns as rows in a table instead of tabs in a workbook, joins the database enforces, and authorisation expressed as 240 row-level-security policies rather than column omission. Knowing precisely where the first system stopped is most of what made the second one right.

The problem

A single endorsement deal touches four parties who each need a different slice of the same record. The creator supplies identity, address and bank details; the brand client approves talent and reviews video; an internal account team runs the pipeline; and a warehouse ships the physical sample. Coordinated by hand, the same creator's details were re-keyed into a contract, a shipping manifest and a payment run — three chances to get one bank account number wrong.

Two constraints shaped every decision that followed. Creator rates and banking details must never reach the client, because the gap between what the brand pays and what the creator receives is the agency's margin. And there was no budget for infrastructure — no server, no database, no front-end to host — so the whole thing had to run on the Google Workspace licence the company already paid for.

Key decisions

  • Data isolation by projection, not permission

    The master pipeline carries 74 columns, creator rate and banking fields among them. Each brand client gets a live view of their own campaign built by importing a 43-column subset of it, with a four-column write surface for approvals and feedback. The withheld columns are not permission-protected — they are absent. There is no hidden field to reveal and no sharing setting to get wrong, because a leaked link exposes a document that never contained the data. Permissions fail quietly when someone picks the wrong option; structure cannot fail that way.

  • Configuration as data

    The scripts hold almost no constants. Partner spreadsheet IDs, the A1 ranges to import from, mode switches and Docs template IDs all live in cells at the top of the sheets they govern: the logistics workbook stores the pipeline's file ID and four source ranges in the first row of every brand tab, and the pipeline template stores the logistics file ID beside a label reading Logistic ID:. Wiring a new campaign, or repointing an existing feed, is an edit an account manager can make — it needs neither me nor a deployment. That is why roughly 35 KB of script is enough to run a system this size.

  • Engineering around a hard platform ceiling

    Apps Script terminates execution at six minutes, and a full metrics sweep across the roster will always exceed that. The extractor checkpoints at 4.5 minutes, writes its position back to the sheet and schedules a continuation trigger ten minutes out, so a run completes across as many invocations as it needs rather than failing at whatever size first broke it. That position is not hidden state: the control sheet keeps a row per tab marking it processed, still to do, or deliberately skipped, so anyone can open the file and see where the last run stopped. A seven-day freshness check makes re-running harmless, and LockService stops a manual run colliding with the scheduled one.

  • A self-managing lifecycle

    Tabs enrol themselves in weekly tracking for a six-month window and then drop out, so the job's workload does not grow without bound and nobody has to remember to retire a finished campaign. Sheet protection works the same way — 12 ranges scoped to four authorised editors, applied in one action instead of range-by-range on every new campaign. Client feedback is capped at three rounds by the layout itself, with a revision counter and an elapsed-days column, so scope creep surfaces as data rather than as an argument. And 11 timestamp columns, one per stage boundary, make hand-off duration a subtraction rather than a reporting exercise.

Deeper technical detail

Five layers, one join point. A creator CRM holds the talent master — identity, banking, tier, category, audience split, and ten paired columns recording which brands each creator has already worked with and what each of those produced. The campaign pipeline is the hub every other layer joins to. A logistics workbook mirrors the shipping columns for the courier partner. A control workbook drives the batch jobs and payment runs. Client portals project from the pipeline. Nothing integrates with anything except the hub, which is what kept the number of connections linear as campaigns accumulated.

Built for the team that uses it. Every column header is written in Chinese and English, because the account team is. The workbooks are owned by four separate accounts across business development, operations, logistics and me — this was never a personal spreadsheet that grew, it crosses department boundaries and had to keep working when people changed roles.

Integrations and generated artefacts. Engagement metrics via RapidAPI, affiliate GMV via TapReport exports, creator analytics from FastMoss and Kalodata, a Make.com webhook, and the courier's own workspace. Contracts are produced from a Docs template with 15 merge fields, shared view-only by link, and the resulting PDF URL written back to the creator's row. Payment consolidation reduces a 105-tab roster to three triage buckets and one bank-ready payout list.

Longevity. The workbooks were created between December 2024 and June 2025 and were all still being edited nineteen months later. This is a system in continuous production use rather than a prototype — which is also why its limits were worth taking seriously enough to rebuild against.

The problem

To write 2–3 sentences. Source: chrome_extractor.md §1 — a roster of creator usernames in Sheets needing recurring commercial-performance visibility, against two platforms offering no bulk export and no public API.

Key decisions

  • Two deliberately different strategies in one repository

    To write The TikTok extractor scrapes the rendered DOM through a 7-deep cascading selector fallback chain to survive obfuscated hash-suffixed CSS classes. The FastMoss extractor skips the interface entirely. This is a visible engineering progression, not inconsistency.

  • Reverse-engineered request signing

    To write Deriving the fm-sign scheme — sorted-parameter concatenation with a salt, a hand-inlined dependency-free MD5, and a fold-and-XOR transform — replaced a 5–10 second page render with a single HTTP round-trip per creator.

    Framing note from the source doc: foreground the architecture and the impact rather than the bypass. An interviewer may probe the terms-of-service angle.

  • Session-riding instead of credential storage

    To write credentials: "include" reuses the operator's existing authenticated browser session, removing API keys, OAuth service accounts, a secrets vault and token-refresh machinery from the system entirely.

  • Reliability engineering for unattended runs

    To write Per-task 45s timeouts, 15/20/30s fetch aborts via AbortController, stale-response task-ID guards, tab-closure detection, and Apps Script document locks preventing concurrent-write corruption. Errors write back into the row, so no record is silently dropped or left stuck.

The problem

To write 2–3 sentences. Source: property_finder.md §1 — portals advertise straight-line distance to transit; the system's core constraint is that straight-line distance is only ever a prefilter, never a displayed number.

Key decisions

  • The seam was chosen before the engine

    To write Routing sits behind a RoutingProvider interface; the engine swaps with a one-line change and nothing in the app or the 11 pipeline scripts depends on GraphHopper directly. The design specified OSRM via Docker, Docker turned out to be unavailable, and GraphHopper was substituted with that one line. The seam paid for itself during the build rather than hypothetically — which is the point worth making.

  • Batch enrichment, not request-time computation

    To write All expensive geo work happens in offline pipelines; the app reads precomputed values from SQLite, so filtering and sorting across 11 dimensions run client-side with no network round-trip.

  • Failing loudly rather than degrading silently

    To write The enrichment script pings the routing engine first and exits non-zero if unreachable. A silent fallback to straight-line distance would have quietly violated the system's one accuracy guarantee.

  • Null-safe filter semantics

    To write Numeric thresholds exclude a listing only when the value is known and violates the threshold, so a project with a missing price-per-square-foot isn't silently erased. "Not yet routed" is distinguished from "routed, but too far" — absent data never masquerades as a negative result.
